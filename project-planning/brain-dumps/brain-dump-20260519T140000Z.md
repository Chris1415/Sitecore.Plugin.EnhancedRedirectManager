## 1. Idea Summary

Add **regex pattern authoring + a redirect testing surface** to the Redirect Manager. Operators get an explicit Pattern / Regex mode toggle per row in the edit modal (with regex helpers and save-time validity check), plus a new secondary tab on the Full Page workspace ("Manage / Test") where an operator pastes a URL, clicks Test, and sees a **full trace** of how the Content SDK `RedirectsProxy` would evaluate that URL against the current redirect inventory — matched? which map / row / mode / capture groups / final destination / redirect type / flag effects.

The companion PRD-005 (split out per scope_dial phase-per-SDK-surface rule) will add **upstream-proxy drift detection** and an **AI-driven re-sync slash command** scoped to Redirect Manager. PRD-004 is shippable and useful without it.

## 2. Problem Statement

Today the Redirect Manager assumes plain-URL patterns. The Content SDK proxy already supports regex (per-row, no flag needed), but operators have no way to author regex confidently — no mode signal, no validation, and no way to verify a rule actually fires the way they expect. Mistakes are caught only by deploying to the tenant and clicking around production URLs.

PRD-004 closes that loop: explicit regex authoring + an in-app dry-run that mirrors the upstream proxy's matching algorithm exactly.

## 3. Target Users

- **Site administrators** managing redirect inventories — author both URL and regex rules side-by-side; can dry-run a sample URL before publishing.
- **Migration operators** importing legacy inventories — paste an old URL, see whether a rule covers it, fix gaps before the migration goes live.
- **Marketers** authoring marketing campaign redirects — quick "does this work?" sanity check without leaving the app.

## 4. Key SDK Findings (these collapse the design space)

### F1 — No regex/URL storage flag exists in Sitecore

Stock Redirect Map template fields are all SHARED, no `IsRegex` flag (captured 2026-05-13). The proxy auto-detects per-row at runtime via `isRegexOrUrl()`:

```typescript
// content-sdk/packages/core/src/tools/utils.ts
export const isRegexOrUrl = (input: string): 'regex' | 'url' => {
  input = input.slice(0, -1);
  const isUrlLike = /^\/[a-zA-Z0-9\-\/]+(\?(...))?$/.test(input);
  return isUrlLike ? 'url' : 'regex';
};
```

**Consequence:** PRD-004 makes ZERO Sitecore schema changes. The `UrlMapping` field already holds mixed pattern types. The "mode" we expose in the UI is a **per-row editor affordance**, not a stored attribute. (Operator confirmed 2026-05-19: mode chosen manually, not auto-detected on read.)

### F2 — Regex flavor: JS `RegExp`, two accepted forms

```typescript
// redirects-proxy.ts :: getRedirectPatternRegex
const literalMatch = normalizedPattern.match(/^\/(.+)\/([a-z]*)$/i);
if (literalMatch) {
  const [, source, flags] = literalMatch;
  return new RegExp(source, flags || 'i');
}
return new RegExp(normalizedPattern, 'i');
```

- JS literal form: `/pattern/i` → flags honored
- Plain source: `^/path$` → default flag `i` (case-insensitive)
- `escapeNonSpecialQuestionMarks` escapes `?` unless pattern is anchored (`^` or `$` present)

### F3 — Capture-group syntax: numbered only

```typescript
existsRedirect.target = existsRedirect.target.replace(
  /\$(\d+)/g,
  (_, index) => matched[parseInt(index, 10)] || ''
);
```

`$1`, `$2`, … in the destination get substituted from regex capture groups. Plus `$siteLang` for the current site language. **No `$<name>` named-group support.**

### F4 — Match candidates (regex mode)

The proxy tests multiple path candidates derived from the incoming request:

1. `incomingURL` (raw)
2. `normalizedPath` (lowercased, trailing-slash stripped)
3. `getLocaleStrippedPath(incomingURL, urlLocale)`
4. `getLocaleStrippedPath(normalizedPath, urlLocale)`

Each is tested with and without the query string appended. Our simulator must replay this exact ordering or we'll get false negatives.

### F5 — Pre-match filters

- Files (paths containing `.`) are skipped
- Preview-mode and prefetch requests are skipped (irrelevant for our simulator)
- `nextUrl.pathname` is lowercased before match

## 7. Proposed tranche structure

Following operator's emphasis (2026-05-19): always tranche, and **add a testing tranche when assumptions are uncertain — gain clarity early**.

| # | Tranche | Type | Purpose |
|---|---|---|---|
| **T1** | Capture & probe | **test** | Author a regex row directly in Sitecore tenant; round-trip through existing app CRUD; confirm `UrlMapping` decoder preserves regex chars (`^`, `$`, `(`, `)`, `?`, `\`); capture upstream proxy SHA; verify our existing rules display correctly |
| **T2** | Simulator + types | build | Port `isRegexOrUrl`, `getRedirectPatternRegex`, `escapeNonSpecialQuestionMarks`, candidate-path generation into `lib/redirects/proxy-simulator.ts` — RED tests first from upstream fixtures; header comment with upstream SHA + retrieval date |
| **T3** | Edit-modal mode toggle + validation | build | Segmented control + regex helpers + save-time validation + capture-group/destination cross-check |
| **T4** | Test surface tab | build | Tab segmentation; URL input + Test button; full trace output panel |
| **T5** | A11y + theme + reduced-motion polish | build | Theme parity tests; focus management on tab switch; reduced-motion compliance; ≥AA contrast |
| **T6** | Real-tenant smoke | **test** | 5–10 known URLs against the live tenant; simulator predicts → operator verifies against actual Edge behavior |

T1 is a hard gate. If existing app CRUD strips regex special chars on save, that's a quiet bug to fix as Tranche 0 before anything else.

## 8. Open questions for PM agent / PRD

1. **Mode persistence across edit sessions** — operator picked "manual mode" (2026-05-19). On re-open of an existing row, default is Pattern. If operator authored a regex row yesterday and reopens it today, they see it labeled Pattern even though it'll match as regex at runtime. Is that acceptable, or should we surface a subtle hint ("this pattern contains regex characters") without auto-switching? My recommendation: surface the hint, never auto-switch.
2. **`$siteLang` token UX** — should the destination input recognize `$siteLang` as a chip / first-class token (like `$1`)? Or document it in the regex-helpers panel only?
3. **Locale handling in tester** — the proxy strips locale prefixes during match. Should the tester accept a "request locale" input alongside the URL, or default to `en` (matches PRD-003's locale simplification)?
4. **Trace output format** — Markdown-style step list, structured cards per stage, or both? I lean structured cards with copy-as-JSON for debugging.
5. **What's the smallest evidence I can show to prove the simulator matches upstream?** PM should require we copy upstream unit-test fixtures (if any exist in `redirects-proxy.test.ts`) into our `proxy-simulator.test.ts` to guarantee parity.

## 11. Risks

- **R1 — Upstream proxy bugs we replicate** — `isRegexOrUrl` has `input.slice(0, -1)` which drops the last character before testing. That looks like a bug; we replicate it for parity but document it loudly. Capture as ADR.
- **R2 — Existing CRUD strips regex chars** — addressed by Tranche 1 probe before any feature work starts.
- **R3 — `$siteLang` token in tester output** — our simulator needs to know the site's language; passed in via test input or resolved from the active site context. Decision in PM discovery.
- **R4 — Catastrophic backtracking on user-supplied regex** — operator could author a regex like `(a+)+$` that hangs the simulator. Mitigation: wrap match calls in a setTimeout race or worker. PM should decide whether this is in-scope for PRD-004 or punted.
- **R5 — Operator confusion when manual mode picks Pattern but pattern contains regex chars** — the proxy will runtime-match it as regex anyway. We need a clear UX signal ("hint: this pattern contains regex characters; runtime will treat it as regex").
