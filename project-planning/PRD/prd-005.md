## 1. Executive Summary

PRD-005 closes the parity contract introduced by PRD-004 over time, not just at port time. PRD-004's `proxy-simulator.ts` is a verbatim local port of upstream `RedirectsProxy` with 100% upstream-fixture parity (M2) **at the moment of porting** — but upstream is a living codebase, and the trace will silently diverge as Sitecore/content-sdk evolves. Today there is no signal.

PRD-005 ships two co-shipping pieces, deliberately layered to keep AI complexity out of the deployed Marketplace app:

1. **In-app passive detector** — a banner on the Test tab that surfaces when the upstream `RedirectsProxy` on Sitecore/content-sdk **`dev`** (the tracked branch for v0 — see § 1 amendment note) has a different SHA than the baseline this simulator was ported from. Detection is **on-demand only** (operator clicks "Check upstream"); **SHA-mismatch only** (no content-level diff in the app); dismissable per session. Unauthenticated GitHub API (60/hr/IP) is sufficient.
2. **Dev-time slash command `/sync-redirect-proxy`** — lives in the **product repo's `.claude/commands/`**, NOT inside the deployed app. An engineer invoked by an operator-flagged banner runs the slash command locally, Claude Code fetches latest upstream, proposes a verbatim re-port patch via its normal edit flow, regenerates `__fixtures__/upstream-cases.json` via the existing AST extractor (ADR-0042), runs `npm test -- proxy-simulator`, and on accept auto-bumps the SHA in `upstream-snapshot.json`.

PRD-005 also lands a **foundational refactor**: migrate the baseline SHA + retrieval metadata out of `proxy-simulator.ts`'s header comment into a dedicated JSON snapshot at `site/lib/redirects/__fixtures__/upstream-snapshot.json`. Header comment becomes documentation referencing the JSON; JSON is the source of truth for both the in-app check and the slash command. **PRD-005 also switches the tracked branch from `dev` (PRD-004's capture) to `main`** — main is what real tenants run; this requires a one-shot re-snapshot at T1 (and possibly a re-port if the SHAs differ substantively).

**Zero new Sitecore SDK surfaces.** One new HTTP integration (GitHub REST API, unauthenticated, public read). No new extension-point routes. No server-side OAuth. **No CSP changes** — verified at authoring that `next.config.mjs` is empty and no app-level CSP is set, so the in-app `fetch()` to `api.github.com` works without modifications.

**Branch tracking amended at /architect (2026-05-22):** The original D12 / T1 plan was to track Sitecore/content-sdk's `main` branch. A live probe at architecture time returned HTTP 404 — the watched file does not exist on `main` (default branch is `dev`). To keep M1/M2 verifiable, PRD-005 v0 tracks **`dev`** (same as PRD-004's port baseline). Promote to `main` via a snapshot-JSON edit once Sitecore publishes it. ADR-0044 amended in place to reflect this; no new ADR.

## 2. Problem Statement

PRD-004 ships a verbatim local port of upstream `packages/nextjs/src/proxy/redirects-proxy.ts` + `packages/core/src/tools/utils.ts` (Content SDK). The simulator is **100% fixture-parity at port time** (M2 satisfied), with the baseline SHAs recorded in `proxy-simulator.ts`'s header comment (`30b0db8f…` for `redirects-proxy.ts`, `e6153e5e…` for `utils.ts`, both from `dev`).

But upstream is a living codebase. Within weeks or months, the actual `RedirectsProxy` running in production-deployed Sitecore tenants will have moved, and our simulator's trace will silently diverge — a quirk of `isRegexOrUrl` may be fixed, a new pre-filter may be added, a flag-effect may be reworked. The Test tab promises a faithful preview; without drift detection, that promise has a half-life.

Three secondary problems:

- **The baseline SHA is buried in a comment.** Parsing comments as data is fragile; if the comment block ever gets reflowed by an automated formatter, drift detection breaks silently.
- **PRD-004 tracked `dev` branch.** `dev` is in-progress code; `main` is what real tenants run. The drift signal should target the branch that actually deploys, not the branch in flight.
- **Manually re-porting an upstream change is expensive.** Tracking the upstream repo, recognizing a relevant commit, reading the diff, mapping it back to the simulator, regenerating fixtures, running tests — easily 1-2 hours of focused engineer time. A slash command compresses that to "review the proposed patch + accept".

PRD-005 closes the loop over time: in-app passive detection (banner) for operators, and a dev-time AI-assisted resolution path (slash command) for engineers.

## 4. Target Users

Two distinct user types, deliberately separated:

- **Operators using the Test tab** — see the banner. Their job is "know that the simulator may be stale before I rely on its trace". They click "Check upstream", they read the banner, they tell their engineer. They do NOT run the slash command.
- **Engineers maintaining the Redirect Manager codebase** — run the slash command at dev time when an operator or scheduled check (future PRD) has flagged drift. Their job is "re-port the changed function(s) verbatim, regenerate fixtures, run tests, commit". They have Claude Code installed locally with edit access to the product repo.

This split keeps the deployed Marketplace app simple (one GitHub API call, one banner, no LLM, no API keys, no cost) and concentrates AI complexity in the dev-time tool where it belongs.

## 6. User Stories

### US-1 — Operator checks if the simulator is current

**As an** operator about to run a Test-tab simulation
**I want** to confirm the simulator is up-to-date with the upstream `RedirectsProxy` before I trust the trace
**So that** I can either rely on the trace, or ask my engineer to update first

**Acceptance Criteria:**
- **AC-1.1** — The Test tab's left rail contains a "Check upstream" button (placement per UI design). Primary action style.
- **AC-1.2** — Clicking the button fires the drift check. Button shows a loading spinner; button is disabled until the check resolves.
- **AC-1.3** — When SHAs match baseline: an inline "In sync with upstream `dev`" message appears with `lastChecked` timestamp. No banner.
- **AC-1.4** — When SHAs differ: an `UpstreamDriftBanner` renders above the trace area with copy "Upstream `RedirectsProxy` has changed since this simulator was ported. Trace may be subtly inaccurate. Ask your engineer to run `/sync-redirect-proxy` to update. (Last sync: `<retrievedAt>`)."
- **AC-1.5** — Banner has a dismiss (X) button — keyboard-accessible, ARIA-labeled. Dismiss writes to `sessionStorage` under key `rm-drift-banner-dismissed`; banner hidden for current browser session. Reappears on next page reload.
- **AC-1.6** — While the banner is visible, all Test-tab interactions (URL input, Test button, trace area) continue to work normally. Banner is informational only.
- **AC-1.7** — The "Check upstream" button never auto-fires — no `useEffect` auto-fetch on Test tab mount. Operator must click.

### US-2 — Operator sees a graceful error when the check fails

**As an** operator clicking "Check upstream"
**I want** to know when the check itself fails (rate limit / network / 404)
**So that** I can retry or escalate appropriately, without thinking the simulator is broken

**Acceptance Criteria:**
- **AC-2.1** — On HTTP 403 (rate limit): banner shows "GitHub API rate limit reached. Try again in N minutes." N comes from the `X-RateLimit-Reset` response header (relative-time formatted). Retry button present but disabled until reset time.
- **AC-2.2** — On HTTP 404 (file moved or branch deleted): banner shows "Upstream file not found at expected path. This may indicate a Sitecore refactor — engineer review required." No retry button.
- **AC-2.3** — On network error or HTTP 5xx: banner shows "Couldn't reach GitHub. Try again." with an enabled retry button.
- **AC-2.4** — All error states render in muted styling (NOT red/alert tones — operators see this on a normal day). Banner role is `status`, not `alert`.
- **AC-2.5** — Test-tab interaction never blocks during error states.

### US-3 — Engineer re-syncs the simulator after a drift signal

**As an** engineer notified that operators see a drift banner
**I want** to run `/sync-redirect-proxy` in Claude Code inside the product repo and have it propose a verbatim re-port patch
**So that** I can review, accept, and ship the update in a single session

**Acceptance Criteria:**
- **AC-3.1** — Slash command `/sync-redirect-proxy` is registered in the product repo's `.claude/commands/` directory. Invoking it from Claude Code initiates the flow.
- **AC-3.2** — Step 1 of the flow: read `site/lib/redirects/__fixtures__/upstream-snapshot.json`. Report current baseline SHAs.
- **AC-3.3** — Step 2: **two fetches per watched file** — (a) raw content from `https://raw.githubusercontent.com/Sitecore/content-sdk/main/<watched-file>` (for diff / AST extractor input); (b) latest commit SHA from `https://api.github.com/repos/Sitecore/content-sdk/commits?path=<file>&sha=main&per_page=1`. Both unauthenticated. Compare each file's returned commit SHA against the corresponding baseline in `upstream-snapshot.json`. If both files' SHAs match baseline: print "Already in sync — no patch proposed" and exit cleanly.
- **AC-3.4** — Step 3: regenerate the gitignored `site/lib/redirects/__fixtures__/_upstream-source.ts` staging file from the freshly-fetched upstream raw content (the AST extractor reads this file).
- **AC-3.5** — Step 4: read current `site/lib/redirects/proxy-simulator.ts`. Identify which ported helpers / orchestrator body lines are affected by the upstream diff. Propose a verbatim re-port patch via Claude Code's edit flow (one hunk per affected function/helper).
- **AC-3.5b** — Step 5: operator reviews each proposed hunk via Claude Code's edit flow. Operator may accept all, accept some, or decline. On decline of any hunk: see AC-3.10. On full accept: continue to Step 6.
- **AC-3.6** — Step 6: on operator accept (Step 5 succeeded with all hunks accepted): run `npm run extract:upstream-fixtures`. Verify `upstream-cases.json` regenerated cleanly (file changed; case count printed).
- **AC-3.7** — Step 7: run `npm test -- proxy-simulator`. Print per-case pass/fail summary.
- **AC-3.8** — Step 8a (test green): update `site/lib/redirects/__fixtures__/upstream-snapshot.json` with new SHA(s) + `retrievedAt` + new `fileHash` per watched file. Print "Drift resolved — commit the changes (simulator + snapshot + fixtures together). The in-app baseline updates after the next deploy." Slash command exits cleanly.
- **AC-3.9** — Step 8b (test red): leave simulator edits in place but DO NOT bump the snapshot. Print failing case names. Print "Patch left for refinement; snapshot un-bumped. Either refine the port further OR add a `knownDivergences[]` entry to `upstream-snapshot.json` with rationale, then re-run."
- **AC-3.10** — If the operator declines the proposed patch in Claude Code's edit flow: slash command exits with no changes; snapshot un-bumped; print "No changes applied."
- **AC-3.11** — Slash command is idempotent. Running it twice in a row when SHAs match produces "Already in sync" both times. No spurious file edits.
- **AC-3.12** — `knownDivergences[]` entries are honored: when proposing a patch, the slash command SKIPS proposing changes to functions listed in `knownDivergences[]` and prints "Skipping function X — known divergence per snapshot entry at <ISO>."

## 7. Functional Requirements

### A — Snapshot foundation

- **FR-A1** — `site/lib/redirects/__fixtures__/upstream-snapshot.json` exists with this shape (committed verbatim, not gitignored):
  ```json
  {
    "schemaVersion": 1,
    "branch": "dev",
    "repository": "Sitecore/content-sdk",
    "originalPort": {
      "branch": "dev",
      "ports": [
        { "path": "packages/nextjs/src/proxy/redirects-proxy.ts", "sha": "30b0db8fe768b83f03fd6b9772b0d3e14711c6b2", "portedAt": "2026-05-20T18:32:24Z" },
        { "path": "packages/core/src/tools/utils.ts", "sha": "e6153e5e80c2076704cad0876eec3b85ec3a1a9f", "portedAt": "2026-05-20T18:32:24Z" }
      ]
    },
    "watchedFiles": [
      { "path": "packages/nextjs/src/proxy/redirects-proxy.ts", "sha": "<commit-sha>", "retrievedAt": "<ISO>", "fileHash": "<sha256-of-content>" },
      { "path": "packages/core/src/tools/utils.ts", "sha": "<commit-sha>", "retrievedAt": "<ISO>", "fileHash": "<sha256-of-content>" }
    ],
    "knownDivergences": []
  }
  ```
  The `originalPort` field preserves the ADR-0038 verbatim-port provenance from PRD-004 (`dev` branch SHAs captured at port time). It is set once during T1 migration and never modified afterward — it is the historical audit anchor. `watchedFiles` is what the drift detector + slash command read for current baseline; `originalPort` is for audit.
- **FR-A2** — `proxy-simulator.ts` header comment is rewritten to reference `upstream-snapshot.json` as authoritative. The header retains ADR references + human prose; the data-bearing SHAs move to the JSON. A brief one-line in the header notes the original-port provenance (`Originally ported from Sitecore/content-sdk@dev as of 2026-05-20 — see __fixtures__/upstream-snapshot.json originalPort field for full SHAs.`).
- **FR-A3** — T1 baseline capture: fetch current `dev` SHAs for the 2 watched files (`main` was originally planned per D12 but does not exist on upstream — `/architect`-time probe returned 404; ADR-0044 amended). Compare against PRD-004's `dev` SHAs (`30b0db8f…` / `e6153e5e…`). If SHAs are identical (upstream hasn't moved since PRD-004 port): commit the snapshot JSON with `branch: 'dev'` and proceed to in-app detector build. If `dev` has moved: run a re-port within the same PR; the snapshot reflects post-re-port `dev` SHAs. Promotion to `main` becomes a single-line snapshot-JSON edit when Sitecore publishes a `main` branch.

### B — GitHub API client

- **FR-B1** — `site/lib/upstream-drift/github-client.ts` exports `async function getLatestCommitSha(filePath: string, branch: string): Promise<{ ok: true; sha: string; retrievedAt: string } | { ok: false; reason: 'rate-limit' | 'not-found' | 'network' | 'unknown'; retryAfterSeconds?: number }>`.
- **FR-B2** — Implementation: single `fetch()` to `https://api.github.com/repos/Sitecore/content-sdk/commits?path=<encoded-file-path>&sha=<branch>&per_page=1`. Headers: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`. No `Authorization` header (unauthenticated).
- **FR-B3** — Response handling:
  - 200 + non-empty array → `{ ok: true, sha: data[0].sha, retrievedAt: <now> }`
  - 200 + empty array (path moved or never existed at this branch) → `{ ok: false, reason: 'not-found' }`
  - 403 + body containing `rate limit` → `{ ok: false, reason: 'rate-limit', retryAfterSeconds: <from X-RateLimit-Reset header> }`
  - 404 (repo or branch removed) → `{ ok: false, reason: 'not-found' }`
  - Network error / 5xx → `{ ok: false, reason: 'network' }`
- **FR-B4** — No retries. Caller (the hook) decides whether to retry.
- **FR-B5** — Module is `'use client'`-safe (called from a hook in a client component). No `'server-only'` directive.

### C — Drift check hook

- **FR-C1** — `site/hooks/use-upstream-drift.ts` exports `useUpstreamDrift()` returning `{ state, lastChecked, errorReason, retryAfterSeconds, recheck }`.
- **FR-C2** — `state` values: `'idle'` (initial; nothing fetched) | `'checking'` (in-flight) | `'in-sync'` (all SHAs match snapshot) | `'drifted'` (at least one SHA differs) | `'error'` (any FR-B3 non-ok case).
- **FR-C3** — `recheck()`: reads the snapshot JSON (via a static `import` — Next.js bundles it), calls `getLatestCommitSha` for each watched file sequentially (not parallel — keep simple and respect rate limit), compares each result.SHA against snapshot.watchedFiles[i].sha. State transitions: `idle` → `checking` → `in-sync` | `drifted` | `error`.
- **FR-C4** — No `useEffect` auto-fetch on mount. The hook is idle until `recheck()` is called.
- **FR-C5** — Concurrent calls to `recheck()`: hook returns early if `state === 'checking'`. Button is also disabled in this state (UI layer).
- **FR-C6** — `lastChecked` updates on every terminal state (success or error). Persists for the component's lifetime (no localStorage).

### D — Drift banner

- **FR-D1** — `site/components/full-page/UpstreamDriftBanner.tsx` is a Test-tab-scoped component.
- **FR-D2** — Renders conditional on `state === 'drifted'` AND `sessionStorage.getItem('rm-drift-banner-dismissed') !== '1'`.

- **FR-D6** — Reduced-motion: any banner enter/leave animation respects `prefers-reduced-motion: reduce` → instant render.

### E — "Check upstream" button

- **FR-E1** — Button lives in the Test tab left rail (exact placement per UI design § 11).
- **FR-E2** — Label: "Check upstream". Primary CTA style.
- **FR-E3** — On click: calls `recheck()` from the hook. While `state === 'checking'`: button shows a loading spinner, label changes to "Checking…", disabled.

## 9. Technical Considerations

### Existing context

- **Platform target:** marketplace (carry-over from PRD-000..004).
- **App architecture, extension points, auth model, router:** all unchanged from PRD-004.
- **Existing SDK surfaces:** `xmc.authoring.graphql` (CRUD), `xmc.preview` (Edge reads), `xmc.publishing` (PRD-003), OAuth client-credentials proxy (PRD-003 server-side route). **PRD-005 adds none of these.**
- **One new HTTP-integration surface:** GitHub REST API + raw content. Public, unauthenticated, single-purpose (read-only fetch of 2 files + their commit SHAs).

### Upstream parity strategy (carry-over from ADR-0038)

PRD-005 reinforces ADR-0038's verbatim-port discipline by making drift visible. The slash command's proposed patch must replicate upstream semantics including quirks (e.g. `isRegexOrUrl` `.slice(0, -1)`). Operators reviewing the patch reject any "improvement" that diverges from upstream. If a deliberate non-port is needed (rare), the operator adds a `knownDivergences[]` entry instead of accepting a divergent port.

### Network access (no CSP changes)

The Marketplace app currently runs inside Cloud Portal (`app.sitecorecloud.io`) iframe. **Verified during PRD-005 authoring: `next.config.mjs` is currently empty; no middleware, layout, or response handler sets a `Content-Security-Policy` header on the app's HTML responses.** The Marketplace iframe inherits Cloud Portal's outer-document `frame-ancestors` policy, but our app's outbound `fetch()` calls are not restricted by an app-level CSP.

Therefore: the in-app `fetch()` to `api.github.com` works WITHOUT any CSP changes in PRD-005. No `next.config.mjs` edits are required.

If a future PRD (or a Sitecore Marketplace platform mandate) introduces an app-level CSP, the migration must include `https://api.github.com` in the `connect-src` directive. `raw.githubusercontent.com` is only used by the dev-time slash command (runs outside the browser via Claude Code's Bash/WebFetch) and does NOT need to appear in an in-app CSP.

### Deploy-cycle assumption

The snapshot JSON is consumed by the in-app detector via a static `import` — Next.js bundles it at build time. When an engineer runs `/sync-redirect-proxy` and the snapshot SHA is bumped, the new SHA only reaches the deployed Marketplace app AFTER the next Vercel build + deploy. Operators clicking "Check upstream" between the slash-command run and the next deploy will continue to see the stale baseline (and the drift banner) until the deploy completes. AC-3.8's "Drift resolved — commit the changes (...)  The in-app baseline updates after the next deploy." message states this explicitly. R8 records the risk.

### GitHub API rate limit

Unauthenticated: 60 requests/hour per IP. PRD-005's traffic profile:

- "Check upstream" button click: 2 requests (one per watched file).
- Slash command run: 2 GitHub API requests + 2 raw content fetches (still within rate limit comfortably).

For an operator clicking 5 times an hour: 10 requests. For an engineering team of 5 sharing an office NAT IP: still well under 60/hr. Acceptable.

If rate limit becomes painful in real usage, PAT auth is FO-5.2 — small uplift.

### Failure modes

- **GitHub API down / 5xx** — banner shows "Couldn't reach GitHub" + retry button. Test tab continues to work.
- **Rate limit hit** — banner shows reset time. Operator waits or asks engineer to use the slash command (slash command runs in a different IP context if engineer is on home/VPN network).
- **Upstream file renamed** (e.g. Sitecore refactors `redirects-proxy.ts` → `redirects-handler.ts`) — `GET /commits?path=…` returns empty array → banner state `'error'` reason `'not-found'`. Engineer manually edits `upstream-snapshot.json` to update the path, then re-runs.
- **Upstream branch renamed** (e.g. `main` → `master`) — `GET /commits?sha=main` 404s → banner state `'error'` reason `'not-found'`. Same recovery as file rename.
- **Schema mismatch** — `schemaVersion !== 1` in snapshot JSON → banner state `'error'` with explicit copy. Engineer migration required.
- **Slash command: tests fail after patch** — simulator edits in place, snapshot un-bumped. Operator decides next step.
- **Slash command: operator declines patch** — slash command exits with no changes; snapshot un-bumped.

### Bundle impact

Static import of the snapshot JSON: file is < 1KB. GitHub client module: ~40 LOC. Hook: ~60 LOC. Banner component: ~80 LOC. Total: <5KB gz comfortably.

### Slash command implementation

`.claude/commands/sync-redirect-proxy.md` follows Claude Code's standard slash-command Markdown format. The file describes the flow procedurally (steps 1-8 from FR-G2). Claude Code interprets it as a procedural prompt + uses its built-in tools (Read, Edit, Bash, WebFetch) to execute.

### Test surface (smoke)

T6 operator smoke procedure: bump baseline SHA in `upstream-snapshot.json` to a known-stale value (e.g. `0000000…`). Click "Check upstream" → banner appears. Run `/sync-redirect-proxy` in Claude Code → fetches latest → proposes patch (or "Already in sync" if real upstream SHAs match the bumped value's path — unlikely with zero SHA). Accept proposed patch. Tests run; expect GREEN. Snapshot JSON updates. Click "Check upstream" again → "In sync".

## 13. Risks and Mitigations

- **R1 — `dev` has moved substantively since PRD-004 port, requiring a re-port at T1** (probability: low–medium, impact: medium)
  - Mitigation: T1 is a baseline-capture + spike-and-decide tranche. If `dev` SHAs are identical to PRD-004's recorded SHAs, no re-port. If small drift (1 helper change), absorb into T1. If large (major upstream refactor in the ~2 days since PRD-004 ship), split PRD-005 into 005a (snapshot + detector) + 005b (slash command) per OQ-5 default. **Note:** original PRD-005 plan tracked `main`; architecture-time probe found `main` 404s on upstream so v0 tracks `dev` instead (ADR-0044 amendment).
  - Trigger: T1 spike output > 2 simulator function changes OR > 1 helper signature change → file as decision point

- **R2 — False-positive whiplash from comment-only upstream changes** (probability: medium, impact: low)
  - Mitigation: banner copy says "Upstream changed; review the diff" NOT "drift detected". Slash command's diff view makes it obvious when the change is comment-only — operator can bump the SHA without re-porting.

- **R3 — GitHub API rate limit hit by a team sharing egress IP** (probability: low, impact: low)
  - Mitigation: on-demand only (D3) limits per-operator traffic to ~10/hr typical. Banner shows reset time gracefully. PAT auth is FO-5.2 if it becomes painful.

- **R4 — `next.config.mjs` accidentally gets an app-level CSP added during PRD-005 (or by a future PRD) that omits `api.github.com`** (probability: low, impact: medium)
  - Mitigation: PRD-005 leaves `next.config.mjs` untouched (FR-F1); T5 structural guard asserts no `Content-Security-Policy` directive is introduced in this PRD's scope. Documented in § 9 for the next engineer who looks at this code.

- **R5 — Slash command's AI-proposed patch is subtly wrong (parity break)** (probability: medium, impact: medium)
  - Mitigation: test-run step (AC-3.7) runs `npm test -- proxy-simulator`; SHA bump (AC-3.8) only happens on green. Failed-test state is fully recoverable (no committed change).

- **R6 — Operator dismisses banner, forgets about drift, ships a stale trace** (probability: medium, impact: low)
  - Mitigation: dismissal is per-session only (D7); reappears on next page reload. Banner copy includes `lastChecked` so operator can re-validate if uncertain.

- **R7 — Sitecore renames branch (`main` → `master` or vice versa)** (probability: very low, impact: medium)
  - Mitigation: `branch` field in snapshot JSON is editable; recovery is a JSON edit + re-snapshot. Banner state `'error'` reason `'not-found'` surfaces the issue explicitly.

- **R8 — Static import of snapshot JSON delays in-app baseline updates by one deploy cycle** (probability: certain, impact: low)
  - The snapshot is bundled at build time; an engineer-side SHA bump only reaches the deployed app after the next Vercel deploy. Between slash-command success and deploy completion, operators clicking "Check upstream" continue to see the stale baseline (and the drift banner). This is intentional — no server-side runtime fetch of the snapshot to keep the app simple.
  - Mitigation: AC-3.8's success message states this explicitly ("The in-app baseline updates after the next deploy."); operator can choose to dismiss the banner for the session in the meantime.

- **R9 — Bundle delta exceeds NFR-1 (5KB gz)** (probability: very low, impact: low)
  - Mitigation: T5 measures bundle delta vs pre-PRD-005 baseline; if exceeded, profile and trim.

- **R10 — `knownDivergences[]` array becomes a dumping ground that hides real drift** (probability: medium long-term, impact: medium)
  - Mitigation: each entry requires `reason` + `upstreamSha`; slash command surfaces existing entries when proposing patches; T6 operator smoke includes "does the divergence list look reasonable?" check. Periodic operator review is the long-term safeguard.
