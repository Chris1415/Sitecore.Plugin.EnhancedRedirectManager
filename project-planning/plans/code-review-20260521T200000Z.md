## Major Findings

### M1 — Stateful `g`-flag regex race condition in `simulate()` — `$siteLang` substitution silently skipped on concurrent calls

**File:** `site/lib/redirects/proxy-simulator.ts:324`
**Category:** Correctness
**Severity:** Major

**Description:**

`REGEXP_CONTEXT_SITE_LANG` is declared as a module-level constant with the `g` flag:

```ts
const REGEXP_CONTEXT_SITE_LANG = /\$siteLang/gi;
```

The `g` flag is used so `.replace()` replaces ALL occurrences of `$siteLang` in a destination string. However, a `g`-flagged `RegExp` retains its `lastIndex` after each `.test()` call. At line 563:

```ts
if (REGEXP_CONTEXT_SITE_LANG.test(matchedFinalTarget)) {  // sets lastIndex = 15
  matchedFinalTarget = matchedFinalTarget.replace(REGEXP_CONTEXT_SITE_LANG, ...);
  // .replace() resets lastIndex to 0
}
```

If a second `simulate()` invocation starts between the `.test()` and `.replace()` calls of the first (e.g. user double-clicks the Test button), it sees `lastIndex = 15`, starts the test mid-string, and returns `false` even if the destination contains `$siteLang`. The substitution is silently skipped. The final URL retains the literal `$siteLang` string and is incorrect.

Verified via `node --input-type=module`:
```
test1: true  lastIndex: 15
test2 (concurrent call, same string): false  lastIndex: 0
```

This is not caught by existing tests because tests call `simulate()` sequentially.

**Fix applied:** Reset `REGEXP_CONTEXT_SITE_LANG.lastIndex = 0` immediately before each `.test()` call, with an explanatory comment.

**Regression test added:** Two new test cases in `proxy-simulator.test.ts` — "REGEXP_CONTEXT_SITE_LANG stateful regex regression (code-review M1)" describe block — verify that consecutive `simulate()` calls on the same input produce identical results, and that the `g` flag still replaces ALL occurrences of `$siteLang`.

### M2 — `ResultCard` pagination: infinite "Load more" button caused by `hiddenCount` computed against `rowsConsideredTotal` instead of `rows.length`

**File:** `site/components/full-page/ResultCard.tsx:136`
**Category:** Correctness
**Severity:** Major

**Description:**

The simulator caps `rowsConsidered` at 20 items (via `input.rules.slice(0, Math.min(evaluatedRows, 20))`) but `rowsConsideredTotal` reports all evaluated rows (can be larger). In `UnmatchedCard`:

```ts
const rows = result.rowsConsidered;         // max 20 items
const total = result.rowsConsideredTotal;    // could be 25, 100, etc.
const showCount = expanded ? Math.min(chunkLimit, rows.length) : INITIAL_SHOW;
const hiddenCount = total - showCount;       // BUG: total vs rows.length
```

After expanding: `chunkLimit = 20`, `rows.length = 20`, `showCount = 20`, `hiddenCount = total - 20`. If total was 25, `hiddenCount = 5`. The "Load more" button says `+ 5 more rows`. User clicks: `chunkLimit = 70`, but `showCount = Math.min(70, 20) = 20` (rows.length cap), so `hiddenCount = 5` again. The button never disappears. This is an infinite loop in the UI — the button renders forever but reveals no new rows.

**Fix applied:** Changed `hiddenCount` to `rows.length - showCount`. This correctly reflects "how many of the items we actually have to display are still hidden", and goes to 0 once all 20 are revealed.

**Regression test added:** "load-more button disappears after all rows are revealed (regression: infinite loop fix M2)" in `ResultCard.test.tsx` — creates a result with 20 `rowsConsidered` / 25 `rowsConsideredTotal`, clicks expand, asserts no load-more button remains.
